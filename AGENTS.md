# AGENTS.md — STM32F103C8T6 firmware

This file is the contract for any AI agent working in this repository.
Read it before touching code. It encodes facts that are expensive to rediscover
and cheap to respect.

---

## 1. What this project is

Bare-metal **STM32F103C8T6** ("Blue Pill") firmware on STM32Cube **HAL**.

| Fact | Value |
|------|-------|
| Core | Cortex-M3, no FPU (all floats are soft-float, avoid them) |
| Flash / RAM | 64 KB / 20 KB — hard limits, see §5 |
| SYSCLK | 72 MHz from 8 MHz HSE, PLL x9 |
| Bus clocks | AHB 72 MHz, APB1 36 MHz, APB2 72 MHz |
| Fallback | If HSE does not start the code runs on HSI/2 x16 = 64 MHz and logs `[WARN]` |
| Console | USART1, PA9 (TX) / PA10 (RX), **115200 8N1** |
| LED | PC13, **active low** |
| Debug probe | ST-LINK over SWD (PA13/PA14) |

There is **no SWO trace pin** on this board (the cheap ST-LINK V2 dongles only
wire SWDIO/SWCLK/GND/3V3). UART is the only observation channel. Never design
a change that can only be validated with a debugger attached.

## 2. Two build tracks — same compiler

| Track | Command | Purpose |
|-------|---------|---------|
| **CMake + armclang** | `powershell -ExecutionPolicy Bypass -File tools/build.ps1 [-Config Release]` | The track agents use. Fast, emits `compile_commands.json`, `-Wall -Wextra`, size report. |
| **Keil MDK (UV4)** | `... tools/build.ps1 -Keil [-Config Release]` | The track that ships. `MDK-ARM/STM32F103C8T6.uvprojx`, targets `Debug` and `Release`. |

Both use **Arm Compiler 6 (armclang)**, so they do not diverge: the two tracks
currently produce **byte-identical `.bin` images** in both configurations
(verified by SHA-256). If CMake builds but UV4 does not (or the reverse), that
is a real defect — report it, do not work around it.

The Keil track needs `Keil.STM32F1xx_DFP` installed under
`ARM/PACK/Keil/STM32F1xx_DFP/`. `tools/setup.ps1` downloads and installs it.

**Adding a source file means editing three places**, and `-Keil` refuses to run
if they disagree:
1. `APP_SOURCES` / `HAL_SOURCES` in `CMakeLists.txt`,
2. the matching `<Group>` in `MDK-ARM/STM32F103C8T6.uvprojx`,
3. the include path, if the new file lives in a new directory.

The compiler options are duplicated too: `Cads/MiscControls` in the `.uvprojx`
carries the same `-std=c99 -ffunction-sections -fdata-sections -fno-common
-Wextra -Wno-unused-parameter` as `target_compile_options`. Keep them equal.

The CMake track does **not** use CMake's linker driver: `armlink` is invoked from
`CMakeLists.txt` with `cmake/stm32f103c8tx.sct`. Changing memory layout means
editing that scatter file, not a linker script.

## 3. Repository layout and who owns what

```
Core/      CubeMX-shaped entry layer: main(), clock tree, vector handlers.
           Rewritten wholesale if the .ioc is regenerated.
App/       Application behaviour. Pure logic lives here so it can be unit tested.
Bsp/       Board specifics: console UART, crash blackbox, board.h pin map.
tests/     Host-side unit tests (gcc, no target needed).
cmake/     Toolchain file + scatter file.
tools/     The agent interface: build / flash / monitor / verify / crashdump / size / test.
external/  Downloaded STM32CubeF1 + HAL. GIT-IGNORED, regenerated by tools/setup.ps1.
MDK-ARM/   Keil project. The .uvprojx is hand-maintained and version controlled;
           Objects/, Listings/, DebugConfig/ and RTE/ next to it are generated.
```

**Edit freely:** `App/`, `Bsp/`, `tests/`, `tools/`, `CMakeLists.txt`, `docs/`.
**Do not edit:** `external/` (vendor code), `Drivers/` if present,
startup `.s` files, `cmake/*.sct` (without explicit human approval).
**Edit only in lockstep with `CMakeLists.txt`:** the source list inside
`MDK-ARM/*.uvprojx`.
**Ask first:** anything that changes pins, clocks, or interrupt priorities.

HAL modules are opt-in. To use a peripheral:
1. add `#define HAL_XXX_MODULE_ENABLED` to `Core/Include/stm32f1xx_hal_conf.h`
   (and its `#include`),
2. add `${HAL_DIR}/Src/stm32f1xx_hal_xxx.c` to `HAL_SOURCES` in `CMakeLists.txt`.
Skipping step 2 fails at link time with `undefined symbol HAL_XXX_Init`.

## 4. The loop you must close

```
edit  ->  tools\build.ps1  ->  tools\test.ps1  ->  tools\size.ps1  ->  tools\verify.ps1
                                     |
                              on failure: tools\crashdump.ps1
```

| Command | What it proves |
|---------|----------------|
| `tools\build.ps1` | Compiles and links with warnings enabled |
| `tools\build.ps1 -Keil` | The shipping MDK project still builds and agrees with CMake |
| `tools\test.ps1` | Hardware-free logic still behaves (host gcc) |
| `tools\size.ps1` | The image still fits (flash < 90 %, RAM < 70 %) |
| `tools\verify.ps1` | Builds, flashes, and the expected `[BOOT]`/`[HB]` lines appear on UART |
| `tools\monitor.ps1 -List` | Which COM port the USB-TTL adapter is on |
| `tools\crashdump.ps1` | Symbolicates the last HardFault record from the log |

**Definition of done:** `tools\build.ps1` exits 0, `tools\test.ps1` exits 0,
`tools\size.ps1` exits 0, and — if hardware is attached — `tools\verify.ps1`
exits 0. Never claim a firmware change works from reading the code alone.

## 5. Hard constraints on this part

1. **64 KB flash / 20 KB RAM.** The build prints totals; `tools\size.ps1` enforces
   a budget. Stack is 1 KB and the crash blackbox reserves the last 256 bytes of
   RAM (`0x20004F00`–`0x20004FFF`). Do not grow the stack without re-measuring.
2. **No `%f` in printf.** Floating-point formatting pulls in several KB of
   library code. Log integers and scale them (`temp_mc` = millidegrees).
3. **No blocking in interrupt context.** ISRs set a flag or push to a ring
   buffer; the main loop does the work. `bsp_log_printf` is *not* ISR safe.
4. **`volatile` for anything shared with an ISR**, and read-modify-write shared
   counters inside a critical section (`__disable_irq()` / `__enable_irq()`).
5. **PB3 / PB4 / PA15 are JTAG by default.** Using them as GPIO requires
   `__HAL_AFIO_REMAP_SWJ_NOJTAG()` *and* enabling the AFIO clock. Keep SWD
   (PA13/PA14) working or you lose the ability to reflash.
6. **PA9/PA10 belong to the console.** Repurposing them removes the only log.
7. **No dynamic allocation.** No `malloc`/`free` anywhere in firmware code.

## 6. Coding conventions

- C99, `-Wall -Wextra` clean. Fix warnings; do not silence them.
- `STD_`/`HAL_` types at the boundary, plain `uint32_t` internally.
- Names: `module_function()`, static helpers are `static`, file-scope state is
  `s_`-prefixed. Constants are `UPPER_CASE`.
- Every public function has a one-line comment saying *why* it exists, not what
  the code obviously does.
- Log lines are machine readable and stable:
  `[BOOT] ...`, `[HB] n=... t=...`, `[WARN] ...`, `[FAULT] ...`.
  `tools\verify.ps1` greps for these — changing the format changes the tests.

## 7. Debugging playbook

1. Run `tools\monitor.ps1 -Seconds 30` and reproduce.
2. If the board went silent or reset itself, run `tools\crashdump.ps1`. The
   firmware stores PC/LR/CFSR/HFSR in `.noinit`, resets, and prints the record
   on the next boot. `cause=...` lines name the fault bits.
3. Map PC to source: `tools\crashdump.ps1` already does symbol lookup; for
   file:line it uses `arm-none-eabi-gdb` when available.
4. To prove the blackbox path end to end, build with
   `-DCMAKE_C_FLAGS=-DBSP_FAULT_SELFTEST` and call `bsp_fault_trigger_selftest()`.
